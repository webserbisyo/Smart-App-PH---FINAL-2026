# Database blueprint (MVP A)

Status: **approved 2026-11-17 (decision T96: D1 to D9 as recommended); built 2026-11-17** as 7 migrations (`supabase/migrations/20261117100000` to `…160000`) with 99 pgTAP tests in `supabase/tests/`. Section 13 lists where the build differs from the first plan. The full illustrated version (diagrams, normalization walkthrough, data dictionary, sources) is the downloadable "Database blueprint" doc; this file is the short core plan that agents follow.

This replaces the old schema in `docs/archive/SMART_APP_PH_BLUEPRINT.md` section 13 and `docs/archive/SYSTEM.md` section 7, which date from 2026-11-03 (before T49 to T95) and must not be built from.

Source-of-truth order when things disagree: `decisions.md` → `api.md` + the Zod schemas in `packages/core` → the built screens → this file. A disagreement is a stop-and-ask, never a silent pick.

## 1. Shape

```
browser ─HTTPS─► NestJS (Railway, Singapore) ─pooler 5432─► Postgres (Supabase, Singapore)
                     │                                       ├─ auth  (Supabase Auth: owners, members)
                     ├─ supabase-js: Auth + Storage only      └─ storage (files; bytes counted in media_files)
                     └─ jobs: expire unpaid, delete old proofs, clear unconfirmed uploads, send outbox
```

- Everything goes through NestJS (T34, rule 13). The browser never reaches Postgres, PostgREST or Realtime. Uploads use a signed upload URL from NestJS (T65).
- No pg_cron, pg_net, edge functions, Realtime or rule-carrying triggers. Timed work is a NestJS job; live updates are polling or SSE from NestJS.
- Plain, portable SQL. Supabase-only features are limited to Auth and Storage, both behind NestJS, so a later move to AWS or another Postgres is a connection-string change plus Auth and Storage adapters.

## 2. Conventions

| Topic                  | Rule                                                                                                                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Names                  | lowercase snake_case, plural tables, `<table>_id` foreign keys                                                                                                                        |
| Primary keys           | `id uuid primary key default gen_random_uuid()` (Postgres 17: no `uuidv7()` until 18). Junction tables use a composite key                                                            |
| Tenant                 | every shop table has `tenant_id uuid not null`. Children use a composite foreign key `(tenant_id, parent_id) → parent (tenant_id, id)`, so a row can never point into another shop    |
| Time                   | `timestamptz` stored in UTC. `business_date date` = the Manila day, written by NestJS (a time zone conversion is not immutable, so it cannot be a generated column)                   |
| Money                  | `integer` centavos, `check (x >= 0)`. Never `money`, `numeric` or floats                                                                                                              |
| Text                   | `text` with `check (char_length(x) between 1 and N)`, never `varchar(n)` or `char(n)`                                                                                                 |
| Closed lists           | `text` + `check (x in (...))`, copied from the `as const` list in `packages/core` (rule 5). No Postgres enums                                                                         |
| JSON                   | only for a document saved and read whole and checked by Zod: storefront draft and published content, an avatar record, a tracking payload. Never for something we filter, join or sum |
| Computed, never stored | plan status, member stamp balance, member segments, Home numbers, variant price, storage used per kind. The rule lives once in `packages/core`                                        |
| Deletes                | `on delete cascade` from `tenants` down; `restrict` where history needs the parent (an ordered item, a prize variant, a file in use)                                                  |
| Append-only            | `stamp_entries`, `order_events`, `consents`, `shop_activity`, `audit_log`: no update or delete grant, so even the API cannot rewrite them                                             |

## 3. Who can touch what (access model, D1)

- Roles: `app_api` (shop and storefront work) and `app_admin` (the founder's Super Admin), both `nologin`. NestJS connects with the project's pooler connection string and runs every request in one transaction that starts with `set local role app_api` and `select set_config('app.tenant_id', $1, true)` (plus `app.member_id` or `app.user_id` when known).
- The tenant comes only from `tenant_members` for the signed-in owner, or from the slug or order token lookup for the storefront (rule 12), never from the URL or body as-is.
- RLS on every table. Policies use `private.current_tenant()`, not `auth.uid()`. `anon` and `authenticated` get **no** grants and no policies, so the Data API sees nothing even if it is left on. Turn the Data API off in the Supabase dashboard once NestJS reads through `pg`.
- Grants are checked before RLS: tables get only the verbs the API needs (append-only tables: `select, insert`).
- Functions: business functions that move money, stock-like counts or stamps (`place_order`, `add_stamp`, `use_reward`, `claim_prize`, `next_order_no`) are `security invoker`, `set search_path = ''`, execute granted to `app_api` only. `security definer` only in the `private` schema for the two lookups that must cross the tenant wall (`private.tenant_by_slug`, `private.order_by_token`) and for the Auth trigger. This follows Supabase's guidance ("never create a security definer function in an exposed schema") and narrows AGENTS rule 8 to the private schema (D1).
- Supabase secret key: only in `apps/api` env, used only for Auth admin calls and Storage signed URLs.

## 5. Keeping data right when two things happen at once

| Risk                                              | Guard                                                                                                                                    |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Two customers take the last limited prize         | `update stamp_cards set quantity_left = quantity_left - 1 where tenant_id = $1 and quantity_left > 0` → 0 rows = `reward_all_claimed`    |
| Two orders take the last slot                     | `pg_advisory_xact_lock(tenant, slot)` then count the slot's orders before insert                                                         |
| Two orders pass an item's daily limit             | conditional update of `item_daily_counts` (`where qty + $n <= limit`)                                                                    |
| Two order numbers the same                        | `order_counters` row lock (upsert)                                                                                                       |
| A double tap places two orders or adds two stamps | `client_key` unique + `on conflict do nothing` returning the first result                                                                |
| Two staff move the same order                     | `update orders set status = $new where id = $id and status = $expected` → 0 rows = `invalid_transition` and the fresh order is sent back |
| A stamp balance below zero                        | lock the member row (`select … for update`), check the sum, then insert                                                                  |

No new error codes: each guard answers with a code already in `api.md`. Isolation stays at the default `read committed`; each guard above is a single conditional statement or a lock.

## 6. Jobs (NestJS, D5)

Every minute: expire unpaid transfers past `pay_by` (`expired`, stamps and prize quantity returned, one transaction each). Every hour: remove uploads not confirmed in an hour. Every day: delete payment proof files older than 30 days (rows keep the reference), expire exports, drop unconverted leads past 180 days. Every minute: send `notification_outbox` and `track_events` with retry and back-off. Jobs are idempotent and take an advisory lock so two API copies never run the same job twice.

## 7. Indexes

An index on every foreign key column, plus: `orders (tenant_id, business_date)`, `orders (tenant_id, status) where status in (open statuses)`, `orders (tenant_id, scheduled_at) where scheduled_at is not null`, `orders (tenant_id, member_id, placed_at desc)`, `orders (pay_by) where payment_status = 'unpaid'`, `stamp_entries (tenant_id, member_id, created_at)`, `media_files (tenant_id, kind) where deleted_at is null`, `order_messages (order_id, created_at)`. Home, the Orders footer and Members read from these; no summary tables in A (T70).

### 7.1 The Home sales summary is fully supported (T69, T70, T83, T84)

The Sales card stays in MVP A with everything it shows. "No summary tables" only means the numbers are added up from the orders when Home asks, not copied into a second table that could drift.

| Part of the card                                                                      | Read from                                                                                                                   |
| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Sales total for the period (Today, Yesterday, 7 days, 30 days, This month, own dates) | `orders.total` by `business_date`, leaving out `cancelled` and `expired` (H2, the same rule as the Orders footer)           |
| Hour-by-hour or day-by-day chart, busiest hour or day                                 | `orders.placed_at` in Manila time, grouped by hour or `business_date`                                                       |
| Paid, To check, Not paid yet bar                                                      | `orders.payment_status` and `payment_proofs.status` (To check = a pending proof, the same orders as Needs you)              |
| "Where it is" rings (drawer, GCash, Maya, each bank)                                  | `orders.payment_method` + `payment_account_id` → `payment_accounts` (removed accounts kept, so old money still has a place) |
| Pace against a usual weekday, best sellers, how they ordered, members today           | `orders`, `order_lines`, `members`, same indexes                                                                            |

The index `orders (tenant_id, business_date)` makes a 30-day read touch only that shop's rows for those days. If a shop ever grows past what this reads quickly (measured, not guessed), a daily summary table is added then as a planned redundancy, filled by the same NestJS job, with no change to the card.

Size estimate (not measured): about 2 to 3 KB per order with its lines, events and messages, so the 500 MB free database holds roughly 150,000 orders across all shops before files, which live in Storage.

## 8. Files and Storage

Buckets: `menu`, `look`, `qr`, `profile` (public read through the CDN), `proofs` and `plan-proofs` (private, short signed links). Paths are `<tenant_id>/<kind>/<uuid>.<ext>`. Uploads are shrunk on the phone (T65), go through a signed upload URL for the exact size, and count only after NestJS confirms them. Storage objects are not in Supabase backups: the export (T66) and a weekly bucket copy are the file backup.

## 9. Personal data (Data Privacy Act, not legal advice)

Collect only what the order needs. Customer data never goes to logs. A member who asks to be removed is anonymised (`erased_at`, name and contacts blanked on the member and their orders); totals stay for the shop's books. Proof photos go after 30 days. Leads go after 180 days unless converted. A breach plan (notice to the NPC within 72 hours) is in `launch.md` before the first paying shop. The legal details were read from secondary sources only (privacy.gov.ph blocked the cloud browser): have them checked before launch.

## 10. Build order (one migration per step, each with RLS, grants, policies and pgTAP tests)

1. Platform core: roles, `private.current_tenant()`, tenants, tenant_members, reserved_slugs, platform tables, revoke `public.rls_auto_enable()` (D7)
2. Shop setup, and `media_files` (other tables point at it from here on)
3. Catalog
4. Members and consents
5. Orders, payments and push
6. Stamp card
7. Exports, billing, activity, help mode, tracking, outbox, audit

Each step: write the migration, the pgTAP tests (cross-shop reads return nothing, append-only tables refuse update and delete, every guard in section 5), regenerate types, switch that area's adapter in `packages/data` from mock to API, run the e2e. Applied migrations are never edited; a mistake is fixed by a new migration. The seed (`seed:demo`) loads the 5 demo shops from `packages/core/src/demo` through the API, so the seed tests the API too.
